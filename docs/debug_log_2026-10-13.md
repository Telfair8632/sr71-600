## Issue List (chronological)

### 1. Pico 2 Completely Invisible When Plugged Into the PC

| Item | Content |
|---|---|
| Symptom | No serial port, no RP2350 drive letter, no response with BOOTSEL held while plugging USB; background polling confirmed zero activity on the USB bus |
| Cause | The micro-USB cable was charge-only, with no D+/D- data conductors |
| Fix | Replaced it with a data cable |
| Reasoning | I used "guaranteed behavior" as a touchstone: the BOOTSEL bootloader is burned into the chip ROM, so as long as the data lines conduct it **must** enumerate as a mass-storage drive regardless of whether Flash is empty. It did not appear → the fault was in the cable/port, not the board |
| Key concepts | RP2350 ROM built-in USB boot (BOOTSEL mode = USB mass storage); charge-only vs data cables; VID/PID identification (Raspberry Pi = 0x2E8A); the Pico 2 has no power indicator LED, so there is no visual way to tell whether it is powered |

### 2. Boot Banners Such As `reset cause: WATCHDOG` Never Visible in the Serial Console

| Item | Content |
|---|---|
| Symptom | After dragging the UF2 over, the board rebooted and ran immediately; by the time I opened the serial terminal the boot banner had already finished printing — it could never be seen |
| Cause | The Pico SDK's USB virtual serial port (CDC) **silently discards** all printf output until the host opens the port |
| Fix | Built with `-DPICO_STDIO_USB_CONNECT_WAIT_TIMEOUT_MS=8000`: at startup the firmware waits up to 8 seconds for the host to connect before printing the banner |
| Reasoning | Acceptance evidence must be observable — evidence that is unreachable because of timing equals no evidence |
| Key concepts | USB CDC "connection" is an event (the host asserts DTR); differences between a virtual serial port and a hardware UART |

### 3. Two Bugs in the Test Script Itself

| Item | Content |
|---|---|
| Bug A | After reset, "wait for the serial output to fall silent before wrapping up" — the firmware printed one line per second, so it never went quiet and the script waited forever |
| Bug B | The expected reboot banner in the `w` test was misjudged as an "unexpected reset": right after I sent `w`, one in-flight status line re-set the verdict flag (race condition) |
| Fix | A: switched to collecting for a fixed 5 seconds; B: introduced a separate phase flag `w_phase` for "after sending w" instead of reusing a flag that the data stream could overwrite |
| Reasoning | Running a 2-minute smoke version before the 30-minute official run was exactly how to surface this class of problem cheaply (both bugs were caught by the smoke/first runs) |
| Key concepts | Race conditions; expected vs unexpected events must be separated by an explicit state machine; USB re-enumeration breaks already-open serial handles |

### 4. [Tonight's Main Thread] level4 Rebooted in a 2.5-Second Loop After Flashing

| Item | Content |
|---|---|
| Symptom | The serial console connected and received the boot banner, then dropped about 1.9 s later, in an endless loop (11 banners observed in 30 seconds) |
| Root cause | The firmware drove GP4/GP5 with the `i2c1` controller, but **the I2C function on this pin pair belongs to the I2C0 controller**. With the controller-pin pairing wrong, I2C transactions never saw their completion flag, so `mpu_detect()` hung forever; nothing fed the watchdog during the hang → 2-second timeout reset → the loop |
| Fix | `#define I2C_PORT i2c1 → i2c0` (one line), plus up to 10 retries added to mpu_detect (guarding against a cold-start NACK from a module not yet powered-up-ready being misread as failure) |
| Investigation path (the key part) | ① Timing fingerprint: the disconnect moment ≈ 1.9 s after the banner, exactly the `watchdog_enable(2000)` period → pinned the fault to "stuck in mpu_detect with nobody feeding the watchdog"; ② Hypothesis 1 (wrong): the bus was being dragged low = module power was reversed → the instruction I gave was to swap the power leads → reverse power, chip heating up (I unplugged it in time; the module survived) — **lesson: check existing evidence such as "is the module LED on" before issuing a rewiring instruction**; ③ Evidence review: the LED had been on the whole time before the swap → power had been correct all along → hypothesis rejected; ④ Wrote a bus-diagnostic firmware (the Pico acting as its own multimeter): logic-level test + pull-low-and-release test → **BUS-FREE, the bus was not clamped at all**; ⑤ Hypothesis upgraded to a controller/pin pairing error; ⑥ The diagnostic firmware re-probed using I2C0: transactions completed normally (proof that it does not hang when the pairing is correct) but returned NACK; ⑦ Changed to continuous probing once per second → stable ACK from 0x68 from the first second onward → the NACK in ⑥ was a cold-start artifact, and the whole picture became clear |
| Key concepts | Pin multiplexing: each GPIO's I2C function is bound to a **specific** controller instance (GP4/GP5 = I2C0; GP2/GP3 and GP6/GP7 = I2C1), and the SDK does not validate the pairing for you; an I2C controller and physical pins are two different things; the watchdog reset chain (hang → timeout → reset); using the MCU itself as the test instrument when no multimeter is at hand; the false-negative risk of a "one-shot probe" (devices need time to be ready after power-up) |

### 5. Static |a| = 0.80g at Rest (Acceptance Expects ≈1.0g)

| Item | Content |
|---|---|
| Symptom | Static acceleration magnitude 0.79~0.87g, stable in every attitude |
| Analysis | \|a\| is attitude-independent (the gravity magnitude is constant) → 0.80 both flat and tilted → a scale problem, not a placement problem; the tilt test read stable, non-jumpy values in every attitude → a uniform scale offset (~20%), not a single damaged axis |
| Possible causes | A compatible-clone MPU6050 with loose factory scale, or a mild after-effect of the reverse-power incident |
| Impact | pitch/roll are computed from **ratios between axes**, so a uniform scale error does not propagate; the gyro is entirely unaffected → usable at the debug stage |
| Follow-up | Add a 1/0.80 scale correction in the firmware before installation, or replace the module with a genuine GY-521 |
| Key concepts | A stationary accelerometer outputs gravity, 1g, regardless of attitude — this "invariant" is itself a self-test; how to tell scale error from a damaged axis (watch which kind of violation breaks the invariant) |

## Methodology Takeaways

1. **Timing signatures are fingerprints**: disconnect time × watchdog period = direct evidence for locating the hang point
2. **Use guaranteed behavior as a touchstone**: BOOTSEL must enumerate; static |a| must be 1g — cut the fault domain with "what must physically hold"
3. **Change one variable at a time, and gather evidence before acting**: tonight's worst mistake (reverse-powering the module) came from issuing a rewiring instruction before checking the evidence already on hand
4. **No instrument? Build one**: 20 lines of firmware turned the Pico into a multimeter/bus probe
5. **Beware false negatives from one-shot measurements**: continuous observation beats a single sample (the cold-start NACK artifact)
6. **Smoke-test before long runs**: the 2-minute version caught both bugs in the script
